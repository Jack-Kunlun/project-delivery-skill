# 渐进接管旧项目

技术老旧、缺少测试或没有台账，并不意味着必须重写项目。先建立可信的现状图景和可维护范围，再在每次变更中逐步增加质量约束。

## 确认接管状态

| 现有材料/能力 | 当前应记录的基线 | 不要声称 |
| --- | --- | --- |
| 有源码和可运行的本地环境 | 记录启动条件、代表性场景、当前输出和问题 | 本地能运行就表示生产环境健康 |
| 有源码，但无法运行或缺少依赖服务 | 记录尝试、失败条件、源码观察和恢复任务 | 根据源码推断就等于行为通过验证 |
| 没有 Git 历史、使用旧软件包或备份散落各处 | 识别允许修改的副本、快照时间和文件哈希；标注来源缺口 | 把最新文件时间当作官方版本，或臆造提交历史 |
| 只能访问生产环境 | 记录获授权的只读观察或已脱敏材料；登记获取副本或测试环境的需求 | 在生产环境试写、自动收集敏感数据或直接升级 |
| 文档与实现冲突 | 并列记录“文档化要求 / 实现观察 / 决策待定” | 假定旧实现就是正确需求，或默认按旧文档修改代码 |

如果本次任务只为接入项目跟踪，将环境恢复、依赖更新和产品修复登记为后续任务；未经授权不要执行。启动命令可能迁移数据库、访问生产环境或调用付费服务。先检查环境和脚本实际行为，并使用获授权的隔离或只读方式。

## 最低限度的现状基线

只记录本任务涉及的领域；不要求一次覆盖每个模块：

- **业务与能力：**主要角色、业务流程、模块入口，以及哪些内容已存在、仅有文档说明或尚不清楚。
- **技术与运行时：**实际框架、运行时、声明的依赖、启动/构建方式、必需服务和配置名称、环境可用性；不要复制秘密值。支持期限、漏洞等版本敏感结论应根据可靠的当前来源核实；不要只凭项目年限下结论。
- **边界与约束：**数据/状态权威来源、上下游使用方、兼容性约定、重要定时任务/脚本、可写和只读区域，以及人员/服务依赖。
- **质量状态：**已有测试及其实际覆盖范围、代表性行为和视觉快照、用户反馈的问题，以及项目无法运行或问题无法复现的原因。没有测试是一个缺口；不代表测试已经执行，也不代表覆盖率为 0%。若场景分母尚未定义，覆盖率未知。
- **交付状态：**项目能否构建/部署、实际发布方式、可观测能力和已有恢复能力。只记录事实；不要为了接入治理而更改 CI 或生产环境。

版本标识优先使用实际提交或产物摘要。如果没有版本控制，使用明确标记的只读快照或清单哈希。引入 Git、迁移目录或清理备份应作为单独决策；建立记录本身并不包含这些操作。

## 区分三类工作

1. **本次交付：**用户实际要求的行为变更或文档接管，以及其范围和验收条件。
2. **当前安全交付所必需的工作：**例如记录受影响模块的行为、增加可重复检查或建立隔离样例。在任务中说明原因和影响。
3. **历史债务/现代化：**与本任务无关的重构、过时依赖、全面 UI 迁移、历史文档整理等。单独列出以便评估；只有获授权后才排期。不要把既有缺陷记录成这一轮新引入的问题。

若发现与本任务相关的重大安全或数据风险，应暂停危险操作，继续不受影响的盘点，并遵循项目风险规则。不要用“旧系统”为由跳过本任务必须遵守的边界。

## 每项变更的最小切片

1. 选定一个可观察目标，并识别涉及的模块和上下游；写清非目标，阅读相关历史缺陷和限制。
2. 记录足以执行的当前与目标差异及验收条件；不要重建完整的历史 PRD。需求不清时先调查；任何重大行为取舍必须由有权人员决定。
3. **行为变更时，**最好先保存可重复的基线检查，再开始修改。可使用已有自动化测试、受影响边界的特征测试、隔离服务或明确的手工回归步骤。分别跟踪已知错误，避免把错误固化成永久正确的预期；对预期修复另加断言。
4. 做最小变更，并在执行约定中记录兼容性影响；不要趁机替换框架或升级锁文件。
5. 对比前后行为、受影响使用方和必需验收条件。若没有真实环境，应准确报告源码级/本地证据；缺少必需验收时不能改称已通过。
6. 更新台账和现状基线。生效的新检查或经验应成为下一项任务的入口。逐步通过实际变更扩大可维护范围。

项目整体未知不应阻止所有文档接入。它们是否阻碍某项实现或验收，取决于是否影响该项工作的正确性。避免“必须先彻底理解旧系统才能做任何事”和“测试跑不了所以可以免验收”这两种极端。

## “完成接管”的含义

“完成流程接管”仅表示已经建立入口、当前任务/问题、证据边界和可继续的下一步。这不表示历史债务已清零、所有模块都已验收或项目已现代化。应说明哪些模块已有基线、哪些仍未知、下一步由谁负责，以及何时应扩大盘点范围。
