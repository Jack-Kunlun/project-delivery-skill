# 记录模板与可追溯性

以下内容是字段，不是强制文件清单。若已有问题、工单或文档承载相同信息，就补全该记录；小项目可以合并记录。保留项目已有编号。若尚无编号，则定义稳定且唯一的编号方案；不要重复使用或重排历史编号。

可追溯链路：来源/需求 → 任务 → 设计/约定 → 产物 → 用例/证据 → 验收 → 发布/观察。问题应把失败证据链接到修复任务；变更应关联新旧范围；经验应关联具体问题和预防任务。只要能定位，不要求每一项都有独立编号或文件。

## 任务与当前状态

```text
编号/类型/标题：
来源/目标或里程碑：
目标与可观察的验收条件：
范围/非目标/允许的工作区：
责任人/实际接收方：未分配时写明
状态/优先级/目标版本或已承诺日期：适用时注明未知或尚未承诺
依赖/阻塞/下一步行动：
风险及依据/有限检查预算/扩大检查的条件：
适用的设计或约定版本/匹配的经验：
产物/实际检查/证据/验收结果：
尚未验证的事项/遗留工作/恢复点：
```

状态应符合完成定义。完成调查任务可能表示已经得出结论；这不会关闭相关产品问题。任务卡进度应指向同一权威状态，而不是在按角色划分的台账中重复记录。

## 问题（也可以是一种任务类型）

```text
编号/发现或记录日期/报告来源：
观察到的行为/预期行为/实际行为：
候选版本和环境/入口/角色/前置条件/复现步骤：未知时注明
证据级别：用户反馈 / 源码观察 / 已复现 / 修复后复验
严重程度（影响）/优先级（处理顺序）及其依据：
发生/影响/责任归属/验证边界：
负责人及关联模块/调查或修复任务/下一步：
实现根因/原检查为何漏掉：验证前标为假设
修复产物/相似使用方/预防措施及任务：
关闭条件/审查者和证据/后续效果复验：
```

保留无法复现、重复、超出范围、已取消或已转交问题的原因和去向；不要把它们描述成已修复。合并记录时保留原编号，并指向接收记录。问题复发时追加事件并重新评估；不要删除旧的“通过”记录。

## 临时请求与决策

```text
编号/来源原文/记录日期：
类别：澄清或补充 / 缺陷 / 新功能 / 紧急响应 / 想法
原始范围与当前变更/原因：
受影响的需求、模块、使用方、验收和目标版本：
优先级/依赖/排期或风险取舍：尚未评估时注明待评估
决策/决策者及授权依据/它取代了哪项决策中的哪一部分：
关联任务：复用原任务或新建任务，并说明原因
被中断任务的状态/已完成和剩余工作/恢复点/恢复条件：
```

记录想法并不意味着承诺实施；紧急缺陷仍需保留范围和最低必要验证。应通过追加修订替换旧结论；不要悄悄改写用户的原始请求。

## 模块与阶段交接

```text
模块/约定版本/源模块 → 目标模块：
职责/范围内与范围外：
数据与状态权威来源/可写方、读取方和使用方：
输入：来源、格式、前置条件、权限、校验
输出：结构、语义、完成状态、错误和副作用
失败、超时、重试/幂等性和回退责任：按需填写
上游依赖/下游使用方/兼容性或迁移影响：
交付物和版本/实际发送方/接收方：
验收条件/检查和证据/待办事项：
拒绝原因/退回任务/重新验收条件：
```

源码职责是事实；协作职责是约定；未来拆分是计划。三者应分开记录。不要悄悄改变上游语义、绕过权限或吞掉错误来让集成看起来可用。约定变化时跟踪所有受影响的使用方；使用方不明时建立调查任务。不要求把单体拆分成服务。

## 测试用例与证据

```text
用例编号/关联需求、任务、模块和风险：
角色/环境/前置数据（脱敏或隔离）/页面与状态：
步骤/输入/预期断言/明确的失败条件：
级别：源码/单元/模块/数据库/浏览器/视觉/外部集成/生产观察
自动或手动/运行入口：
实际候选版本或快照/规格及设计版本/工具与配置/执行时间：
实际结果：通过 / 失败 / 已跳过 / 受阻 / 未运行
证据位置/关联问题/未覆盖范围/复测触发条件：
```

对于持续变化的文件，仅有路径可能不足以还原候选版本；按项目实际情况补充提交、产物摘要或文件哈希。证据只能存放在仓库批准的位置或获授权的系统中。项目规则要求时，临时测试和大型产物留在本地，并在交付说明中说明其可用性。不要为留痕而提交秘密或所有临时产物。

### UI 对比记录（适用于选定的受影响用例）

```text
关联任务/问题；候选与环境；路由/组件：
状态与数据准备、同时出现的条件区域；视口/主题/语言：
设计修订或局部基线；受影响布局关系或共享使用方：
预期外观/几何关系；实际渲染与测量：
直接视觉审阅及证据（位置或带日期观察）；实际工具：
结果：通过 / 失败 / 未验证；缺陷去向或排除原因：
回归检查入口；剩余检查与恢复动作：
```

按[实际 UI 渲染验收门槛](delivery-gates.md)选择有意义的用例。保留未知与排除项，空记录或仅检查源码不等于视觉验收。

## 事件、已有成果与改进

- **事件：**日期和事件类型、关联编号、实际操作者、先前状态 → 新状态、原因、产物/证据。记录关键开始、阻塞、中断、验收、取消/合并和收尾；不要复制每一条工具日志。回填时区分记录日期和事件实际发生日期。
- **已有成果：**能力/模块、用户可观察行为、源码/历史依据，分别记录实现/验收/发布/生产验证状态、版本/日期（若已知）、限制和当前问题。新缺陷不会抹去历史交付事实。
- **改进/经验：**模式、来源问题、适用触发条件、实现根因和逃逸原因、变更前后规则、受影响模块、预防任务、效果检查和复测时间、替代/退役关系。按[持续改进](improvement.md)闭环。

## 收尾记录

说明本轮完成和未完成的内容、实际验证范围、当前状态、阻塞、下一步、工作区/候选版本身份，以及未提交材料的位置。不要用“后续改进”掩盖验收缺口，也不要默认把计划中的工作分配给不存在的人员或 Agent。
