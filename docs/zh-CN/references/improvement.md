# 问题边界与持续改进

目标是帮助下一项相关任务避免重犯同类错误，而不只是再增加一条经验。

## 先记录问题，再明确边界

即使尚未复现，也要记录问题，并区分已报告事实与推断。记录以下四类边界：

1. **发生边界：**候选版本、入口、环境、角色、数据/状态和触发条件；指出哪些仍未验证。
2. **影响边界：**受影响功能、共享组件和使用方、历史版本、数据/外部副作用；区分已确认影响和可能影响。
3. **责任边界：**谁拥有规则/实现/状态，谁牵头调查和修复，上下游团队如何验收变更；不要仅因错误显示在哪个页面就把问题分配给该页面。
4. **验证边界：**旧检查测了什么、没测什么，证据覆盖哪个候选版本，什么层级能证明当前修复，以及仍有哪些限制。

每个问题都需要负责人和处理去向；跨模块不是让问题无人负责的理由。应调查关键责任归属未知的部分；不要从问题显示的页面推断根因。

## 何时扩大调查或升级处理

| 信号 | 应采取的行动 |
| --- | --- |
| 同一模式再次出现，或用户再次指出同一问题 | 重开原问题或建立关联；检查旧修复、用例和规则为何没有阻止复发 |
| 共享组件/规则在多个页面引发问题 | 列出受影响的使用方，检查共同原因和代表性状态，再针对范围补充检查 |
| 跨模块的数据权威来源或输入/输出语义冲突 | 更新交接约定、失败责任和兼容处理；验证下游验收 |
| 原测试通过，但底层问题仍然漏出 | 区分源码断言、mock 和真实行为的缺口；调整场景/检查级别 |
| 重大安全、权限、数据、迁移、生产或类似影响 | 遵循项目高风险流程，必要时安排独立审查；不能用笼统风险理由绕过强制约束 |
| 修复反复失败或根因仍不清楚 | 停止重复尝试，保留新证据，缩小假设范围，并在项目重试预算内开展有界调查或提出必要决策 |

升级处理应以证据为依据。这不表示每个问题都需要全仓库重构、全量测试或额外审批。扩大范围时，应说明新增影响、检查预算和停止条件。

## 闭环

1. 建立复现，或收集能解释问题的证据，并保留原始失败。无法复现时，记录尝试和下一步。
2. 确认或明确标记为假设：实现为何失败，原设计/审查/测试为何允许其通过。仅写“粗心”不足以说明逃逸原因。
3. 关联修复和预防任务。小问题可以在同一任务中设置不同验收条件，避免重复劳动。预防措施可以是共享组件、检查、约定、设计规范或明确的人工审阅步骤；选择与失败原因相符的措施。
4. 复测原问题和受影响使用方。可行时证明新检查在旧错误上失败、修复后通过。无法自动化时，提供可重复步骤、实际审阅范围和证据；不要声称运行过未执行的自动回归测试。
5. 分别记录验收：修复有效；预防措施已实施；预防措施在后续适用场景中仍有效。若尚未出现后续触发条件，效果检查标记待办。不要因此无限期阻塞局部修复验收，也不要宣称永久预防。
6. 为后续相关变更、共享使用方接入或适用发布安排效果复查责任人/任务。没有新投诉、触发或观察不代表效果已得到证明。

## 让经验成为下一项任务的输入

在项目权威经验/规则记录中写明模式、触发条件、来源问题、适用模块/状态、必需检查、预防任务、证据和效果复查；项目入口应要求相关任务在开始前阅读并关联匹配经验，收尾时记录检查结果。

更新规则时，保留旧规则和新规则、原因、证据、受影响使用方和替代范围。过时或被新设计取代的规则应明确退役；不要从历史记录恢复旧样式。经验应描述可复现模式，不要把某张截图的尺寸或某个项目的默认布局固化成通用规则。

问题复发时追加事件并重新评估边界，保留此前通过的证据，以便查清防线缺口。不要删除失败或覆盖历史来制造持续成功的记录。只有实际执行结果才能证明改进有效；文档、提醒、skill 安装或计划中的 CI 都不能证明自动防护已经启用。
