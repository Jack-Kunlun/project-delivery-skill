# 项目接入与初始记录

## 有界盘点

从入口、目录、配置和当前任务着手，再有选择地阅读资料以解决关键未知。不要以“建立台账”为由审计每个模块。至少回答：

- 哪个仓库/工作区包含实际实现？它处于哪个分支、提交或快照？哪些内容是原型、历史备份或生成产物？
- 项目解决什么问题、谁在使用、目前如何运行或交付？
- 实际存在什么能力和模块？哪些仅在计划、原型或历史记录中提及？
- 需求、设计、接口、任务、缺陷、发布和经验分别以哪里为权威来源？
- 当前目标和已承诺范围是什么？已经完成了什么？有哪些已知问题、依赖和维护限制？

从当前代码和配置、现有文档及历史记录收集证据。如果有可用且能补充证据的已连接工具，可以使用。无法读取外部来源时，记录这一缺口；不要声称各处记录已同步。不要复制秘密、原始生产数据或含凭据的链接。

## 复用、补齐缺口或首次建立记录

**已有项目跟踪：**梳理记录所在位置，同时保留编号、状态和既有责任归属。不要把外部问题系统的状态复制到第二份手工台账；应将仓库入口链接到权威系统，必要的快照须注明日期并标记为非权威。向外部系统写入仍需本任务授权。格式不一致不是重建台账的理由。

把接入/文档工作本身登记到权威台账中（可以关联已有任务），包含开始记录、结果和证据；不要只记录未来的产品需求。如果没有单独的活动日志，将关键事件追加到任务中。补录历史事件时标记为回填；不要伪装成当时已经记录。

**没有项目台账：**先建立适合项目的最小记录集合。默认可以用 `docs/project/README.md` 作为入口，也可以沿用已有项目目录。小项目可以用一份 `docs/PROJECT.md` 包含：

1. 项目概览、范围基线、主要能力和当前运行限制。
2. 已有能力和历史交付：能力、源码/文档/运行证据、验证级别及已知缺陷。
3. 工作与问题台账：当前任务、已知反馈和下一步；尚未知晓的内容标记为待验证。
4. 决策和关键事件、验收证据及下一次恢复点。

继续盘点前先登记当前记录建设任务。如果尚无历史记录，只回填有证据支持的事实。现有代码不能证明它曾在新流程下被验收、发布或管理。保留尚未复现的用户反馈；责任归属不清时，标记待确认，不要把修复分配给错误的项目。

记录随实际使用逐步拆分。可选文件包括 `TASKS.md`、`CHANGES.md`、`ACTIVITY.md`、`ACCEPTANCE.md`、`MODULE-BOUNDARIES.md`、`LESSONS.md` 和 `EVIDENCE.md`。PRD、设计、测试和已交付能力应放在项目已有的相应文件中。不要创建空壳文件。字段可以共用文档，但职责和可追溯性必须清楚。

## 持久指令是初始化的一部分

用户要求初始化、接入或接管项目时，在已授权的项目范围内默认完成这项集成。不要再要求用户重复提出“更新 AGENTS”“记录未来任务”或“让流程自动持续”。仅请求概念建议或只要求提供包脚手架命令，并不授权完整项目接入。

1. **找到实际生效的项目指令文件。**读取现有项目 `AGENTS.md`、适用的 `AGENTS.override.md` 和相关嵌套指令。有效时使用根目录 `AGENTS.md`；缺失时创建它。如果覆盖文件取代了它，就在实际生效的项目文件中集成，避免写入宿主不会读取的指令。保留更高优先级和更具体的规则；不要删除覆盖文件或修改全局用户指令。检查预期工作目录，而不只是仓库根目录。
2. **确定记录地图。**找到实际项目概览、权威任务/问题来源、决策/事件、验收规则和经验记录。小项目可以把这些内容放在同一文档的不同章节。使用有效的仓库相对链接或既有外部权威来源；不要臆造文件，也不要为了套用模板而创建空文档。
3. **合并简洁的持久化区块。**保留集成以外的现有指令不变。使用一个 `project-delivery:begin` / `project-delivery:end` 区块，或扩展已有的等效集成。重复初始化时更新该区块并复用台账/编号，不要追加第二个区块或另起台账。核对用户编辑；不要盲目替换整个文件。README 可以链接入口，但不能代替实际生效的 Agent 指令。
4. **保持生命周期持续生效。**区块要求后续实质任务读取当前记录、执行前登记工作、跟踪变更/问题和相关经验、完成适用验收检查，并留下结果和恢复点。要求在可用时使用 `project-delivery`。Skill 不可用时，具体的本地规则仍然适用；记录可用性缺口，但不要捏造成功调用，也不要因此自动阻塞无关的安全工作。
5. **完成前先验证。**按以下验收检查执行，并把实际结果记入初始化任务。若无法在范围内写入实际生效的项目指令，仍完成已授权的文档工作并记录剩余的集成缺口；不要将持久化初始化标为完成。已有授权意味着无需为常规步骤反复请求批准。

以下是可按项目调整的简洁示例。写入前替换所有占位内容；生成的指令必须脱离初始化对话和作者机器路径也能使用。

```text
<!-- project-delivery:begin -->
## 项目交付工作流
对于实质项目工作，无需等待用户提醒即可应用 project-delivery。可用时使用已安装的 skill；否则遵循这些项目本地规则，并说明 skill 缺失的限制。
- 入口：{实际概览文件的相对路径}。
- 权威记录：{实际任务/问题、决策/事件、验收和经验记录的路径或章节；复用既有外部权威来源}。
- 执行前，读取当前任务、近期决策和相关经验；关联或新建工作项，并定义范围与验收条件。
- 工作期间，记录重要变更、问题、阻塞和恢复点。
- 交接前，运行适用检查；记录实际证据、未解决缺口、任务状态和下一步。验收与发布分开记录。
- 保留现有项目规则和记录权威来源。继续现有工作；不要每项任务都重新初始化项目，也不要假定拥有发布权限。
<!-- project-delivery:end -->
```

写明实际的责任归属/接收方；未知时标记为未分配。一个人可以承担多个职责；不要求固定团队或 Agent 名单。纯粹解释、没有新决策、问题、范围变化或承诺时，不必虚构工作项。

将仓库文档与所在分支一同版本管理。新 worktree 必须包含适用指令和记录；明确交接未提交内容，不要声称其已同步。不要通过指向其他 worktree 的绝对路径维护可变状态。对于外部权威来源，保留其权限和项目映射关系。

## 进度报告

概览应列出产品范围、里程碑、目标/日期承诺、当前验收证据、阻塞、下一步及更新日期。若没有已承诺日期，应明确说明；不要按任务数量估算工期。

优先报告哪些里程碑结果已验收、哪些仍缺少证据。若需要百分比，先定义：

- **分母：**已承诺基线内的交付单元和权重。排除未承诺想法、重复缺陷报告以及单独的行政任务。
- **分子：**按约定完成定义验收通过的交付单元权重。
- **来源和日期：**链接到任务、证据和基线。范围变化时同时保留新旧度量依据；不要通过变更分母美化进度。

不要把任务数、代码行数、通过的测试数量或文档数量直接说成产品完成率。

## 接入验收

检查以下可观察结果，而不只是文件是否存在：

- 实际生效的项目指令包含一份可用的持久化集成；原有规则仍在，并已检查相关覆盖文件/目录范围。
- 具体记录入口均有效。每种状态只有一个权威来源；概览与台账一致；历史、当前状态和目标彼此区分；当前工作和已知问题都有责任人或处理去向。
- 初始化本身有可追溯的任务和证据。重复初始化复用集成和记录，不重复区块、任务或状态来源；再次运行可以在同一工作项中追加事件。
- 新上下文收到项目指令和一个普通、有界的后续请求，**没有**用户点名此 skill 或要求做任务记录。核验实际生成的任务/问题记录、相关检查、结果和恢复点。使用获授权的隔离副本演练，不要虚构线上产品工作。不要把先前对话或预期答案提供给新 Agent。
- 分别说明实际验证了什么：指令内容/链接；新 Agent 是否遵循这些指令；实际宿主是否会自动加载指令/skill。这些验证彼此不能替代。手动向隔离 Agent 提供生成的指令可以验证后续接续行为，但不能证明宿主会自动加载。如果环境不支持接续检查，标记为未验证并留下一项可执行的验证工作，不要声称已通过。

初始化不应要求用户在每个请求中重复这些步骤。完成报告应指出实际生效的指令文件、权威入口、实际接续证据和剩余限制。文档/接续验收不能证明所有产品行为、持续监控或永久预防。对于暂时无法运行的旧项目，按[渐进接管旧项目](legacy-project.md)保留其实际限制。
