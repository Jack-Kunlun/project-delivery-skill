# 项目研发交付流程：Skill 指令中文说明

[中文首页](../../README.zh-CN.md) · [英文指令原文](../../skills/project-delivery/SKILL.md)

本文是当前英文执行指令的完整中文阅读对照。实际安装和执行仍使用 `skills/project-delivery/` 中的英文指令与元数据；本文不注册第二个 skill。修改流程时应同步中英文内容，不能各自演变为不同规则。

Skill 名称：`project-delivery`。适用于项目初始化或接管、首次建账、交付管理，以及已接入项目的后续实质工作。覆盖任务与问题、范围变更、设计、模块交接、验收和复发问题改进。沿用已有记录；单独执行包脚手架命令或询问概念，不自动授权整个项目接入流程。

让工作可以接续、问题可以追踪、交付可以核验。管理资料应服务当前工作，不能把文档数量当成进度或质量。

## 先确定使用路径

1. **已有台账或流程**：读取项目入口、当前任务、最近决定与相关经验；沿用其文件、外部系统、编号和状态，不建立第二份可变状态来源。
2. **没有台账**：按[项目接入](references/adopt-project.md)盘点并首次建账。小项目可以从一份文档开始；先建立可执行记录，不先造一套空文件。
3. **老旧或情况不明的项目**：同时读[老旧项目接管](references/legacy-project.md)，从现状基线渐进接管。没有 PRD、测试、Git 历史或可运行环境也可以记录，但不能伪造验证。
4. **仅询问流程或评审方案**：回答所问或提出建议；没有写入请求或既有项目约定时，不自动接入整个项目。

先核实实际项目根目录、工作区和本次授权。当前目录可能只是原型或备份；候选身份不明时，只继续可以安全进行的盘点，不能拿错项目实施。阅读适用的 AGENTS 和既有规范，保留用户改动。项目自己的安全、测试、设计和发布要求优先于这里的默认模板。

## 初始化的默认动作

请求初始化或接入项目流程，就包含持续接续设置；用户不需要逐项列出这些步骤，也不需要额外要求“后续自动使用”。阅读[项目接入](references/adopt-project.md)，在已授权项目范围内执行：

- 建立或复用权威记录，并登记初始化工作本身。
- 创建或更新实际生效的项目级 `AGENTS.md` 指令入口，同时考虑适用的覆盖文件。仅在 README 放链接不算完成此步骤。
- 写入真实记录位置，以及后续实质工作的开工、过程更新、验收和收工规则。保留已有规则和编号；更新原接入内容，不重复添加。
- 按[自动验收](references/automated-acceptance.md)安装并接通项目自有门禁：复用既有命令和证据，将当前任务关联到权威完成入口，验证失败阻断和有效证据复用。只有脚本但未接入流程，不能称为已执行门禁。
- 验证接入结果，并进行一次没有流程提醒的新上下文接续检查。记录实际执行情况；缺少验证或有效指令文件无法写入时，明确保留缺口。

对于此前已通过本 skill 接入的项目，下次 skill 在已授权项目范围内执行时，应补齐缺失或过时的接续规则，并保留当前记录。接入之后，后续实质工作遵循项目中保存的指令，不需要重新初始化，也不要求用户反复输入 `$project-delivery`。读取当前任务及适用参考即可。这是随任务执行的指令机制，不是后台服务，也不表示每一轮对话都必然加载 skill。

## 每轮工作闭环

1. **恢复上下文**：明确当前目标、基线或设计版本、任务状态、依赖、最近变更、适用经验及未验证项。来源冲突时，区分已观察行为、目标行为和历史。
2. **登记与定界**：实质执行前关联已有任务或创建任务。记录目标、范围与非目标、来源、实际责任、可观察验收条件、依赖、风险和有限验证预算。小步骤归入同一任务，不为每条命令建任务。问题尚未复现也要保留来源、处理入口和下一步。首次接入和文档工作也属于实质工作，必须进入权威台账，不能只登记将来的产品需求。关键事件可以写在任务中，不要求单独的日志文件。
3. **执行与交接**：按项目惯例实施。跨模块工作先明确输入输出、状态权威、失败归属和接收条件。上游完成不代表下游集成通过。同一人承担多个职责也要留下接收证据；不得暗示未实际启动的 Agent 或独立审查已运行。
4. **验证与验收**：先判断证据能否复用，完整通过且范围、候选输入、设计、工具和环境匹配的证据不重跑。只执行缺失、失效或失败的适用检查；没有有效证据时执行本任务完整适用范围，不自动跑全仓库。使用项目可执行门禁及适用强制检查。记录实际候选、环境、工具、结果和缺口。失败退回对应任务，关键未知保持未解决。只有新增影响、检查失败或项目要求时才扩大检查。
5. **收工与接续**：受管理任务通过可执行门禁完成，非零结果不能授予完成状态。使用受控入口更新既有权威台账，并审计无依据的手工完成。外部状态系统使用其支持的受控转换，接入缺口必须说明。更新唯一权威状态台账，追加关键事件和决定，关联产物与证据，记录遗留、阻塞、恢复点和下一步。用户验收与执行者内部验收分开；不能把尚未确认的结果写成用户认可。

沿用项目已有状态体系。没有时可以采用：待澄清 → 待开始 → 进行中 → 待验收 → 已验收。阻塞、取消、合并和重开要保留原因与关联。已实现、已验收、已发布和线上已验证分别记录，不能用笼统的“完成”掩盖环境边界。阶段可合并或标为不适用，但要说明原因和仍需满足的接收条件，不新增逐阶段审批。

## 总进度与变更

- 项目总览同时包含已有产品能力、已交付成果、当前目标、里程碑、风险与依赖、下一步，不能只统计本轮文档任务。
- 每项状态只有一个权威来源。总览是带日期、对应基线的摘要；岗位视图和模块清单只链接任务，不另维护实时状态表。
- 报百分比前先定义范围、完成标准和权重。条件不足时说明具体已验收、待验收或受阻范围；未知既不是 0%，也不是 100%。历史补录必须有证据，不能编造日期、人员、承诺或测试。
- 临时要求先分类：澄清或补充、缺陷、新功能、紧急处置、想法。记录原话或来源、影响和取舍，关联任务及受影响的验收条件。中断工作时保留恢复点。缺陷严重程度与排期优先级分开，插单不自动成为最高优先。
- 已有授权内明确的小变更继续执行。仅在实质产品取舍、范围或日期承诺冲突、不可逆后果等情况下请求决定。写入待办不等于执行或发布授权。

## 可复用的质量约束

- 涉及 UI 的工作，在实现及收尾前读取[交付门槛](references/delivery-gates.md)中的实际渲染验收要求。识别受影响的条件状态及相邻区域，逐项记录设计预期与真实渲染结果。即使构建、单元测试或路由检查通过，必需视觉证据缺失或失败时，UI 验收仍须保持未通过。
- 原型和 UI 交付复用项目现有视觉语言与组件，并检查实际渲染。按[交付门槛](references/delivery-gates.md)核对对齐、间距、长文本和适用状态；生成截图或断言源码文本，不能单独证明视觉正确。
- 测试覆盖以约定的场景集合为分母，区分设计覆盖、执行覆盖、通过覆盖与代码覆盖；标明 mock、跳过、缺少配置和未执行检查。
- 收到“又出现”“反复”“之前修过”等复发信号时，读取[持续改进](references/improvement.md)。问题记录除了调查和修复去向，还要明确预防措施、同类使用方和效果复验如何接续。未复现时可以先写成后续调查的要求，不能虚构已经落实的防线。记录经验不等于已经防止复发。
- 项目经验和规则保存在项目权威记录中，并建立后续相关任务必读的入口。不能因为一个项目的经验就自动修改个人全局记忆、本 skill 或其他项目。
- 随包执行器自动运行已配置检查、复用证据并控制本地完成状态。它不自动推导完整测试覆盖，不持续监控、不防止恶意本地伪造，也不安装远端分支保护。核实实际接入，保留人工审阅与生产边界。

## 交付说明

说明改了什么、改在哪里、完成到哪个层级、实际做了哪些检查，以及遗留和下一步。首次接入给出唯一入口与记录职责；之后只报告增量，避免复述整套流程。提交、推送、发布和对外发送消息仍遵循实际授权与项目已有要求。
